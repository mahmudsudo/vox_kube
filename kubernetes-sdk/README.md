## Entities, not endpoints

This SDK exposes the API as **37 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `remove`, `patch`):

```ts
const client = new KubernetesSDK()
const items = await client.ApiResourceList().list()
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = KubernetesSDK.test({
  entity: {
    resource_quota: {
      test01: { id: 'test01' },
    },
  },
})
const resourcequota = await client.ResourceQuota().load({ name: 'example_name', namespace_id: 'example_namespace_id' })
// resourcequota is the ResourceQuota entity, populated with mock data
// — call resourcequota.data() for the record itself
console.log(resourcequota)
```

## Quickstart

### TypeScript

```ts
import { KubernetesSDK } from '@voxgig-sdk/kubernetes-sdk'

const client = new KubernetesSDK({
  apikey: process.env.KUBERNETES_APIKEY,
  // Required: this API's server URL is templated on these.
  server: {
    base: '<base>',
  },
})

// List all apiresourcelists (returns ApiResourceListEntity[] — .data() for the record)
const apiresourcelists = await client.ApiResourceList().list()
for (const apiresourcelist of apiresourcelists) {
  console.log(apiresourcelist)
}

// Load a specific configmap (returns a ConfigMap)
const configmap = await client.ConfigMap().load({
  name: 'example_name',
  namespace_id: 'example_namespace_id',
})
console.log(configmap)
```

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) declares everything this project owns:
  package names, versions, active features, per-target settings. It is
  written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration merges.** By default, newly generated content is
  three-way merged into existing files, so generator updates and local
  edits usually converge without manual conflict handling. A project can
  opt for plain overwrite instead.
- **Custom features and entire custom targets** arrive through sdkgen
  packages (`voxgig-sdkgen package add`), on the same rails as the
  bundled languages, and `voxgig-sdkgen doctor` reports any drift from
  what a resync would write.

How-to: [customize and propagate templates](https://github.com/voxgig/sdkgen/blob/main/docs/how-to/customize-and-propagate-templates.md).
The full story: [voxgig.com/sdk/custom](https://voxgig.com/sdk/custom).
